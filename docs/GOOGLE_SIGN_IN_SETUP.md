# Google sign-in setup for SARFlow

## Implemented, with activation pending

Optional `/account` and `/login` pages, header entry, Google OpenID Connect authorization-code flow through Auth.js Core, verified-email checks, PKCE/state/nonce, encrypted seven-day HTTP-only session cookies, CSRF and canonical-origin checks, profile display/editing and sign-out. Google client credentials and session secrets are server-only runtime variables. No Google passwords, provider access/refresh tokens or browser authentication sessions were read or saved during implementation.

The username is a display handle, not an alternate authentication method or a globally reserved name. Display name/username edits live in the encrypted session cookie. They are not synchronized across devices and may reset after signing in again. There is no account database, password login, email magic-link delivery or cloud investigation storage in this increment. Existing local investigations are not uploaded. Public exploration stays open.

No real Google OAuth login has been tested because no OAuth client exists yet. Setup and profile UI tests use explicitly synthetic identities; server tests generate transient test credentials in memory. They are not actual Google accounts or evidence of successful Google authorization.

## 1. Create the OAuth web client manually

Open https://console.cloud.google.com/auth/overview and select or create the project you want to own SARFlow authentication.

In Google Auth Platform:

1. Configure Branding with the SARFlow app name, your support contact and the required app information. Enter account/contact information yourself.
2. Choose the appropriate Audience. For initial testing, use an external testing configuration and add your own Google account as an allowed test user when requested. Keep any test-user restriction in mind; this is not public access for everyone.
3. Request only OpenID Connect basic identity: `openid`, email and profile. Do not add Gmail, Drive or contacts scopes.
4. Under Clients, create a **Web application** OAuth client.
5. Use the canonical site origin below. Add the exact redirect URI below. Do not use a rotating Vercel preview domain for the production client.

Authorized JavaScript origin:

```text
https://sarflow-earth-rbhr.vercel.app
```

Authorized redirect URI:

```text
https://sarflow-earth-rbhr.vercel.app/api/auth/callback/google
```

Complete any Google-required branding, ownership, privacy-information or publication checks. Review Google's current requirements before moving the client from testing to public production. SARFlow's use of basic identity does not waive Google's consent and publication requirements.

## 2. Configure Vercel manually

Open the existing SARFlow project: https://vercel.com/rbhr1/sarflow/settings/environment-variables . Add these variables for the **Production** environment. Enter the values directly into Vercel; do not paste them into chat, source files, screenshots or GitHub.

| Variable | Value to enter |
|---|---|
| `AUTH_GOOGLE_ID` | Client ID from the OAuth web client |
| `AUTH_GOOGLE_SECRET` | Client secret from that client |
| `AUTH_SECRET` | A cryptographically random secret of at least 32 characters, generated by your password manager or trusted local tool and entered directly |
| `AUTH_URL` | `https://sarflow-earth-rbhr.vercel.app` |

Do not enable these variables for arbitrary preview deployments. A different development origin needs its own approved callback and configuration. Do not use `VITE_` prefixes for these variables.

## 3. Deploy this implementation, then verify the real flow

The prepared code is in `D:\SARFlow-upgrade-20261107`; it has not been published or activated by this increment. The previously deployed website remains unchanged. Use the project's existing reviewed staging/release procedure after configuration.

1. Confirm `/api/auth/status` returns `enabled: true`, with the canonical origin. This endpoint never returns secrets.
2. Open `/account` on the canonical address. The Google button should be enabled.
3. Click Continue with Google and complete authentication and any consent yourself on Google's domain.
4. Verify that Google redirects to the exact callback above and then `/account`.
5. Check the verified email and profile. Change the display name/username, reload, and confirm they remain for the current session.
6. Sign out and verify `/api/auth/session` no longer identifies you.
7. Confirm maps, the lab and public evidence remain available while signed out.
8. Test a second allowed Google user and confirm accounts remain separate. Test mobile Chrome. The Android WebView wrapper's Google sign-in has not been implemented or verified; Google authentication may require an external system browser.

Never treat cookie attributes, synthetic session tests or a rendered profile as proof that a real Google OAuth flow passed. Inspect application errors without copying secrets, cookies or tokens into reports.
