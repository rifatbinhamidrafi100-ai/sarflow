# Submission checklist and remaining work

This checklist is preparation advice. It is not a complete or verified transcription of the 2026 submission rules.

## Resolve competition eligibility first

- [ ] Register each actual participant and associate the team with the correct local or universal event and official challenge.
- [ ] Verify the final Dancing with the SARs statement and mandatory datasets from the official challenge page.
- [ ] Obtain guidance from your Local Lead/global organizers about SARFlow's existing pre-event code. Disclose its history and separate reused assets from event work. Do not claim that the existing application was all developed during the hackathon.
- [ ] Keep the organizer response and an accurate record of event-period contributions.

The [official 2026 announcement](https://www.spaceappschallenge.org/blog/explore-the-next-frontier-at-the-2026-nasa-space-apps-challenge/) gives November 14–15, 2026. The [2026 event hub](https://www.spaceappschallenge.org/2026/) has indexed submission information, but the full page could not be retrieved in this audit. The [official San Salvador event page](https://www.spaceappschallenge.org/2026/local-events/san-salvador/) lists November 15 at 11:59 p.m. local time for final submission. Confirm the deadline and time zone for the team's own event. November 5 is an internal target.

The [Santiago organizer-hosted page](https://www.spaceappschallenge.org/2026/local-events/santiago-dominican-republic/) restricts beginning the submitted solution before the event. This is evidence that prior work needs clarification, not a final global eligibility decision for SARFlow.

## Obtain the actual form and rules

- [ ] Open the official [submission guide](https://www.spaceappschallenge.org/resources/project-submission-guide/) and [judging guide](https://www.spaceappschallenge.org/resources/judging-awards-guide/) when available; they returned 502 during this audit.
- [ ] Record exact required fields, character/word limits, required source links, demo formats, video/slides limits and AI disclosure instructions.
- [ ] Verify team-size rules, award eligibility, permitted pre-existing work, licensing and public-access requirements.
- [ ] Adapt the draft to those exact fields. No old-year limit has been assumed here.

## Make the demonstration reviewable

- [ ] Provide an approved link that judges can access without the developer's account. The current Vercel preview requires authentication.
- [ ] Test the chosen final link signed out and on desktop/mobile before submission.
- [ ] Check the observation source links, empty states, date labels, error handling, comparison and exports on that exact deployed release.
- [ ] Keep a clearly dated archived example for upstream outages, with its static status visible.
- [ ] Verify the final video/slides open without account restrictions and comply with the actual format limits.
- [ ] Do not use Vercel Ready alone as evidence that the complete app was exercised publicly.

## Make the source reproducible

- [x] Current local source archive with file hashes prepared in this package.
- [ ] With owner approval, commit and push the reviewed current version, or identify the supplied ZIP as the authoritative snapshot. GitHub currently points to an older base.
- [ ] Select a software license after checking ownership and event requirements. None is currently present at project level.
- [ ] Retain dependency manifests, processing requirements, source credits and setup instructions.
- [ ] Exclude credentials, local private datasets, environments, Git history, caches and generated job output.
- [ ] Run relevant checks on the exact final submission source and retain results. Software tests do not establish scientific accuracy.

## Support scientific claims

- [x] Separate real browse imagery/metadata, synthetic teaching grids and calibrated measurement processing.
- [x] State the calibrated-data and validation gap instead of inventing a result.
- [ ] Complete one real compatible calibrated investigation if permitted within event rules and available time.
- [ ] Record product identities, acquisition times, source hashes, grid/masks, processing parameters and uncertainty.
- [ ] Evaluate with a suitable independent reference. Do not use a landslide interpretation as floodwater truth.
- [ ] Report errors, unavailable support and limitations alongside metrics.
- [ ] Avoid "confirmed damage," "real-time global monitoring," "validated flooding," or a percentage accuracy without supporting evidence.

## Credit people and tools accurately

- [ ] Enter actual team names, contributions, event and project URLs.
- [ ] Disclose prior code and OpenAI Codex assistance; add other AI tools only when actually used.
- [ ] Identify any generated voice, image or video and follow the final event policy.
- [ ] Retain dataset-specific credits and terms; EOX background imagery is not NISAR.
- [ ] Never imply NASA endorsement or an official NASA score. Earlier informal ratings were not an audit or judging result.

## Final manual submission

- [ ] Recheck links from an unauthenticated device.
- [ ] Match the final narrative to what the chosen release actually demonstrates.
- [ ] Have the real team review claims, consented names and disclosures.
- [ ] Submit through the official team project page before the verified event deadline, then retain the visible confirmation.

Nothing in this preparation task submitted a form, pushed GitHub changes, promoted production, changed authentication protection or selected a license.
